# FluxDrop Wire Protocol — Specification v1

**Status:** Stable · **Spec version:** 1 (protocol additions v1.1–v4 are additive, see §1.2) · **Canonical implementation:** [`src/lib/fluxdrop/protocol.ts`](../src/lib/fluxdrop/protocol.ts) + [`src/lib/fluxdrop/encoding.ts`](../src/lib/fluxdrop/encoding.ts)

This document is the normative reference for every byte that crosses a FluxDrop connection: the DataChannel binary framing, every opcode, compression, end-to-end encryption, the transfer manifest, and the Socket.IO signaling contract (room/PIN/TTL semantics).

**Conformance:** `bun scripts/protocol-conformance.ts` (exit 0 = conformant). The golden vectors in §10 are generated by that suite from the real encoders and are the quote of record — if you change framing, re-run the suite and update this spec in the same commit.

## 1. Overview & versioning

### 1.1 Design invariants

1. **The signaling server never touches file data.** It relays SDP/ICE and opaque PAKE blobs, enforces room membership, and nothing else. All file bytes flow over a WebRTC DataChannel (DTLS-encrypted by WebRTC itself).
2. **Frames are self-contained.** Every binary frame carries its own transfer id and chunk index. No cross-frame state is required to interpret a frame (resume, out-of-order arrival on parallel channels, and per-chunk ACKs all work unchanged).
3. **Receiver-stored bytes are always ORIGINAL bytes.** Decompression (and decryption) happen before storing. Bitmaps, byte offsets and checksums never see the wire format.
4. **Everything optional is additive.** Unknown manifest fields are ignored; unknown *frame types* are a protocol error (see §12) — fail the transfer gracefully, never the connection.

### 1.2 Versions

| Tag | Added | Contents |
|---|---|---|
| **v1.0** | baseline | 9-byte header, opcodes `0x01`–`0x0c`, manifest schema, signaling events |
| **v1.1** | compression + resume bitmaps + TURN | `CHUNK_DATA_GZ (0x0d)`, manifest `compression` field, `RESUME_QUERY (0x0c)` semantics, `/turn-credentials` |
| **v1.2** | E2EE + previews | `CHUNK_ENC (0x0e)`, `MANIFEST_ENC (0x0f)`, `PREVIEW_REQ (0x10)`, `PREVIEW_DATA (0x11)`, `e2e-relay` |
| **v1.3** | groups + chat + streaming receive | `CHAT (0x12)`, group rooms (N devices), unicast relays |
| **v4** | merkle + clipboard | manifest `merkle` field, `CLIPBOARD (0x13)` |

A peer that understands v1.0 can still receive a v1.1+ *manifest* (extra JSON fields are ignorable). A peer that receives a *frame type* it does not implement MUST treat it as a protocol error for that transfer (graceful failure path), not as a fatal connection error.

## 2. Transport model

```
┌──────────┐  Socket.IO (ws)   ┌──────────────┐   Socket.IO (ws)  ┌──────────┐
│  Sender  │◄─────────────────►│   Signaling  │◄────────────────►│ Receiver │
│ (client) │   rooms/SDP/ICE   │ :3003 relay  │  rooms/SDP/ICE    │ (client) │
└────┬─────┘                   └──────────────┘                  └────┬─────┘
     │                                                                │
     └──────────── WebRTC DataChannel "fluxdrop-0" (SCTP/DTLS) ────────┘
                     binary frames (this spec) — no server involvement
```

* **DataChannel label:** `fluxdrop-0` for the primary channel; secondary parallel channels are `fluxdrop-1`, `fluxdrop-2`, … (send-side only; the receiver binds any `fluxdrop-*` label). `ordered: true`, `negotiated: false`.
* **Max message size:** the WebRTC spec default (65,545 bytes) is the guaranteed portability target — a 64 KiB chunk + 9-byte header fits exactly. Chromium commonly negotiates larger SCTP max-message-sizes; the reference client opportunistically uses up to 1 MiB on the *send* path only when `pc.sctp.maxMessageSize` advertises it, clamped to `[16 KiB, 1 MiB]` at 90% minus the header. A conforming receiver MUST accept frames up to the negotiated max; the manifest's `chunkSize` is the ground truth for framing/offsets (see §8).
* **Binary type:** `arraybuffer`. String messages are never sent; receiving one is a protocol error.

## 3. Binary frame header (9 bytes)

Every DataChannel message — chunk or control — starts with this header, big-endian:

```
byte:   0        1 2 3 4         5 6 7 8
      ┌────────┬───────────────┬───────────────┐
      │ type   │ transferId    │ chunkIndex    │
      │ u8     │ u32 (BE)      │ u32 (BE)      │
      └────────┴───────────────┴───────────────┘
              followed by 0..N bytes of payload
```

| Field | Size | Meaning |
|---|---|---|
| `type` | 1 | Opcode — see §4. Unknown values are a per-transfer protocol error. |
| `transferId` | 4 | First 4 bytes of the sending-side transfer UUID, as **hex**, big-endian-ordered bytes. E.g. UUID `a1b2c3d4-e5f6-…` → bytes `a1 b2 c3 d4`. Short ids are zero-padded on the right (`padEnd`). The receiver echoes this truncated id in its control frames; it is only unique within a room session. |
| `chunkIndex` | 4 | u32 big-endian. For chunk frames: the global chunk number (see §8.3). For control frames: either `0`, or a field-specific value (called out per opcode below). |

Rules:

* A frame shorter than 9 bytes is malformed. The decoder MUST throw; the caller routes it to the error path (transfer-level error, not connection teardown).
* The header-only frame (9 bytes, empty payload) is legal (e.g. `RESUME_QUERY`).
* `chunkIndex` is written with `>>> 0` semantics — never negative.

## 4. Opcode registry

| Opcode | Name | Direction | Body | Since |
|-------:|------|-----------|------|-------|
| `0x01` | `CHUNK_DATA` | sender → receiver | raw chunk bytes (≤ `chunkSize`) | v1.0 |
| `0x02` | `CHUNK_ACK` | receiver → sender | 1 status byte: `0x01` ok, `0x02` fail | v1.0 |
| `0x03` | `MANIFEST` | sender → receiver | JSON: `TransferManifest` | v1.0 |
| `0x04` | `MANIFEST_ACK` | receiver → sender | JSON: `{ accepted: bool, reason?: string }` | v1.0 |
| `0x05` | `TRANSFER_COMPLETE` | sender → receiver | JSON: `{ finalChecksum: string }` | v1.0 |
| `0x06` | `TRANSFER_COMPLETE_ACK` | receiver → sender | JSON: `{ verified: bool }` | v1.0 |
| `0x07` | `TRANSFER_CANCEL` | either | JSON: `{ reason: string }` | v1.0 |
| `0x08` | `RESUME_REQUEST` | receiver → sender | JSON: `{ lastChunkIndex: number }` (also in header `chunkIndex`) | v1.0 |
| `0x09` | `RESUME_RESPONSE` | sender → receiver | JSON: `{ accepted: bool, fromChunkIndex: number, ackedIndices?: number[] }` | v1.0 |
| `0x0a` | `PAUSE` | either | JSON: `{ paused: true }` | v1.0 |
| `0x0b` | `RESUME_STREAM` | either | JSON: `{ paused: false }` | v1.0 |
| `0x0c` | `RESUME_QUERY` | sender → receiver | JSON: `{}` (empty) — "what do you already have?" | v1.0/1.1 |
| `0x0d` | `CHUNK_DATA_GZ` | sender → receiver | gzip(chunk bytes) — gunzip before storing | v1.1 |
| `0x0e` | `CHUNK_ENC` | sender → receiver | E2E envelope: AES-256-GCM(chunk plaintext) | v1.2 |
| `0x0f` | `MANIFEST_ENC` | sender → receiver | E2E envelope: AES-256-GCM(manifest JSON) | v1.2 |
| `0x10` | `PREVIEW_REQ` | receiver → sender | JSON: `{ v: 1, files: [{ i: number, bytes: number }...] }` | v1.2 |
| `0x11` | `PREVIEW_DATA` | sender → receiver | raw head bytes (or E2E envelope of them); header `chunkIndex` = manifest file index | v1.2 |
| `0x12` | `CHAT` | either | JSON: `{ id: string, text: string, at: number }` (≤ 2000 chars); E2E envelope while E2E active | v1.3 |
| `0x13` | `CLIPBOARD` | either | JSON: `{ text: string, at: number }`; E2E envelope while E2E active | v4 (defined; see note) |

**JSON bodies.** Control opcodes (everything except `CHUNK_DATA`, `CHUNK_DATA_GZ`, `CHUNK_ENC`, `MANIFEST_ENC`, `PREVIEW_DATA`, `CHUNK_ACK`, `CLIPBOARD`-when-encrypted) are UTF-8 `JSON.stringify` output after the header. `CHUNK_ACK` is a single status byte. `CHAT`/`CLIPBOARD`/`PREVIEW_DATA` swap their JSON/raw body for an E2E envelope when the E2E session is active (§7).

> **Note on `0x13 CLIPBOARD`:** the opcode and payload shape are fixed in `protocol.ts` for the v4 (4.6) clipboard-sync feature; the reference web client does not emit it yet. Implementations MUST treat receiving it as a no-op (it carries no transfer-state semantics), which also matches the fail-soft rule below.

> **Note on `CHAT` when encrypted:** with E2E active the payload is the sealed envelope, *not* JSON — the generic decoder parses `body = {}` and the router decrypts the raw payload instead (mirrors the manifest/chunk injection guards in the reference hook).

## 5. Opcode reference

Unless stated otherwise: "sender" is the device that created the room, "receiver" joined it. All multi-byte integers are big-endian. All strings are UTF-8.

### 5.1 `CHUNK_DATA (0x01)` — chunk of file bytes

```
[type=0x01][transferId:4B][chunkIndex:4B][bytes...]
```

Payload is a slice of the *concatenated transfer stream* (§8.3): exactly `chunkSize` bytes except the final chunk of the transfer. SHA-256 manifests are computed over these original bytes. The receiver:

1. stores the (original) bytes for `chunkIndex`,
2. immediately replies `CHUNK_ACK(0x01)`.

### 5.2 `CHUNK_ACK (0x02)` — per-chunk delivery acknowledgement

```
[type=0x02][transferId:4B][chunkIndex:4B][status:1B]
```

`status` is `0x01` (stored ok) or `0x02` (rejected). ACKs are advisory for pacing (§11.2): the sender's authoritative completion check is the receiver's `TRANSFER_COMPLETE_ACK.verified`. ACKs are deduped by `chunkIndex` on both sides (a re-delivered chunk after a lost ACK must not double-count).

### 5.3 `MANIFEST (0x03)` — transfer manifest

```
[type=0x03][transferId:4B][chunkIndex=0][manifest JSON...]
```

Body is the full `TransferManifest` object (§8), the *first* frame of every transfer. The receiver parses it, may request previews (§5.16), shows the consent UI, and answers `MANIFEST_ACK`. While E2E is active the manifest goes out as `MANIFEST_ENC` (§5.14) instead — the receiver MUST reject a plaintext `MANIFEST` arriving after the wire-encryption expectation was frozen (anti-downgrade/injection guard).

### 5.4 `MANIFEST_ACK (0x04)` — consent decision

```
[type=0x04][transferId:4B][chunkIndex=0]{"accepted":true} | {"accepted":false,"reason":"declined by user"}
```

`accepted: false` ends the transfer; the sender tears down with `TRANSFER_CANCEL`/room close.

### 5.5 `TRANSFER_COMPLETE (0x05)` — sender signals end of stream

```
[type=0x05][transferId:4B][chunkIndex=0]{"finalChecksum":"<hex>"}
```

Sent after every chunk has been delivered (per-peer). `finalChecksum` is the **concatenation of the per-file hex digests in manifest order** (`files.map(f => f.checksum).join('')`) — an aggregate, not a whole-stream digest; the receiver verifies each file independently against `files[].checksum` and answers with its verdict.

### 5.6 `TRANSFER_COMPLETE_ACK (0x06)` — verification verdict

```
[type=0x06][transferId:4B][chunkIndex=0]{"verified":true} | {"verified":false}
```

`verified: false` MUST trigger the sender's re-send/corruption path (with the Merkle field, the receiver localizes the bad subtree and re-requests only affected chunks; otherwise the transfer re-runs).

### 5.7 `TRANSFER_CANCEL (0x07)` — abort, either side

```
[type=0x07][transferId:4B][chunkIndex=0]{"reason":"user cancelled"}
```

Either side may cancel at any time. The peer stops sending/stores nothing further; the signaling `transfer-cancel` event (§9) mirrors this to the room for UI purposes.

### 5.8 `RESUME_REQUEST (0x08)` — receiver asks to resume

```
[type=0x08][transferId:4B][chunkIndex=lastChunkIndex]{"lastChunkIndex":42}
```

Sent over the DataChannel after reconnect (the signaling layer also carries a `resume-request` relay for orchestration). `lastChunkIndex` is the highest contiguous chunk the receiver has stored.

### 5.9 `RESUME_RESPONSE (0x09)` — sender answers a resume

```
[type=0x09][transferId:4B][chunkIndex=fromChunkIndex]{"accepted":true,"fromChunkIndex":43,"ackedIndices":[0,1,2,5]}
```

`ackedIndices` (optional, v1.1+) is the receiver-stored bitmap echoed back — sparse resume. The sender resumes from `fromChunkIndex`, skipping bitmap-set chunks.

### 5.10 `PAUSE (0x0a)` — flow-control pause

```
[type=0x0a][transferId:4B][chunkIndex=0]{"paused":true}
```

Receiver-driven backpressure (buffer pressure) or a user action. The sender stops emitting chunk frames for that transferId but keeps the channel open. Heartbeats keep the room alive (§9.4).

### 5.11 `RESUME_STREAM (0x0b)` — flow-control unpause

```
[type=0x0b][transferId:4B][chunkIndex=0]{"paused":false}
```

### 5.12 `RESUME_QUERY (0x0c)` — sender asks "what do you have?"

```
[type=0x0c][transferId:4B][chunkIndex=0]{}
```

Used when a *sender* re-sends into a room where the receiver may already have stored chunks (resume from history). The receiver answers with `RESUME_RESPONSE` carrying its bitmap, so already-stored chunks never travel again.

### 5.13 `CHUNK_DATA_GZ (0x0d)` — gzip-compressed chunk

Identical layout to `CHUNK_DATA` but the payload is `gzip(original chunk)` computed *per chunk, independently* (§6). The receiver gunzips before storing/acking. Everything downstream (bitmap, offsets, checksums) is over the ORIGINAL bytes.

### 5.14 `CHUNK_ENC (0x0e)` / `MANIFEST_ENC (0x0f)` — E2E-encrypted frames

```
[type][transferId:4B][chunkIndex:4B][nonce:12B][ciphertext: pt+16B GCM tag]
```

* `CHUNK_ENC` plaintext = the chunk bytes **after** optional gzip (compress-then-encrypt, §7.3).
* `MANIFEST_ENC` plaintext = the manifest JSON (same bytes `MANIFEST` would carry), `chunkIndex = 0`.
* AAD binds the ciphertext to the frame purpose (§7.2).

### 5.15 `PREVIEW_REQ (0x10)` / `PREVIEW_DATA (0x11)` — consent-dialog previews

```
PREVIEW_REQ  (receiver → sender, chunkIndex=0):
[type=0x10][transferId:4B][chunkIndex=0]{"v":1,"files":[{"i":0,"bytes":24576},...]}

PREVIEW_DATA (sender → receiver, chunkIndex = manifest file index):
[type=0x11][transferId:4B][chunkIndex=i][head bytes or E2E envelope of them]
```

The receiver asks for the head bytes of the first ≤ 8 files (24 KiB each in the reference client) to render thumbnails/text snippets in the consent dialog. Strictly **fire-and-forget**: frames are ignored after the ~4 s window or once the transfer is accepted; a preview failure never disturbs the transfer. `v` must be `1`; unknown versions are ignored.

### 5.16 `CHAT (0x12)` — in-room chat

```
[type=0x12][transferId:4B][chunkIndex=0]{"id":"<uuid>","text":"≤2000 chars","at":<epoch ms>}
```

The reference client uses the fixed wire transfer id `"0"` (bytes `00 00 00 00`) for chat, since chat is room-scoped, not transfer-scoped. Encrypted with the PAKE session key (AAD `chat`) while E2E is active; plaintext otherwise. Bad frames are dropped silently (fail-soft).

### 5.17 `CLIPBOARD (0x13)` — clipboard sync (v4, defined)

```
[type=0x13][transferId:4B][chunkIndex=0]{"text":"...","at":<epoch ms>}
```

Opt-in, both-sides-enabled only; sealed with the session key (AAD `clipboard`) while E2E is active, plaintext otherwise. Receivers surface a copy toast rather than writing the clipboard directly (gesture requirement). See the note in §4 — not yet emitted by the reference client.

## 6. Wire compression — `compression: "gzip"` (v1.1)

**When:** the sender may enable per-chunk gzip only when *every* file in the transfer looks compressible (MIME/extension heuristics in `compress.ts`), the total size ≥ 4 KiB (`GZIP_MIN_TRANSFER_BYTES`), the user pref is on, and the runtime has `CompressionStream`. A single incompressible file (e.g. a video) disables it for the whole session.

**How (ordering is normative):**

```
sender:  read chunk ──► gzip(chunk) ──► frame(CHUNK_DATA_GZ, gzipped bytes)
receiver: frame ──► payload ──► gunzip ──► store ORIGINAL bytes ──► CHUNK_ACK
```

* Compression is **per chunk, independent** — every frame stays self-contained (design invariant 2). There is no cross-chunk gzip dictionary.
* `manifest.compression = "gzip"` (§8) MUST be set, so the receiver knows to gunzip `CHUNK_DATA_GZ`/`CHUNK_ENC` payloads. `CHUNK_ENC` under gzip carries ciphertext of the gzipped bytes (compress-then-encrypt).
* Checksums, resume bitmaps, byte offsets, Merkle leaves — all over ORIGINAL bytes, always.
* Additive: a peer that doesn't know the field sees `CHUNK_DATA_GZ` as an unknown frame type → graceful transfer error (by design; both sides of a v1.1+ transfer negotiate via the manifest field).

## 7. End-to-end encryption (v1.2)

### 7.1 Key agreement — SPAKE2 over P-256 (`e2e.ts`)

The room **PIN** doubles as the PAKE password. The handshake rides the signaling relay (`e2e-relay`, §9) as four opaque message shapes, relayed verbatim without server inspection:

```
sender → receiver : { type: 'hello',   v: 1, salt: <hex 16B>, xPub: <hex compressed point> }
receiver → sender : { type: 'reply',    v: 1, yPub: <hex compressed point> }
sender → receiver : { type: 'confirm', v: 1, mac: <hex HMAC-SHA256> }
receiver → sender : { type: 'fail',     v: 1, reason: '...' }        (abort path)
```

* Primitive: SPAKE2 (RFC 9382-shaped) over P-256, M/N points per RFC 9383, PBKDF2-SHA256 15,000 iterations for the password scalar.
* Transcript binds protocol tag `fluxdrop-e2e-v1`, roomId, both device ids, salt, and both ephemeral points. Any MITM/renegotiation changes the derived keys → confirmation MAC mismatch → visible failure.
* HKDF-SHA256 over the shared point + transcript hash yields: `aesKeyRaw` (32 B), `confirmKey` (32 B), `sas` seed (32 B).
* **SAS:** a 6-digit short authentication string derived from the seed, displayed on both ends. A two-leg MITM produces different SAS values on each leg → users see the mismatch.
* A session key is scoped per (room, peer) — group senders hold one independent key per receiver; the receiver exactly one (its sender).

### 7.2 Frame layout & AAD purposes

While the session is active, payload-bearing frames are sealed as:

```
envelope = nonce(12 B) || AES-256-GCM(ciphertext || 16 B tag)
AAD      = UTF-8("fluxdrop-e2e-v1:" <purpose>)
purpose  ∈ { "chunk", "manifest", "preview", "chat", "clipboard" }
```

| Frame | Purpose (AAD) | Plaintext |
|---|---|---|
| `CHUNK_ENC (0x0e)` | `chunk` | chunk bytes after optional gzip |
| `MANIFEST_ENC (0x0f)` | `manifest` | manifest JSON |
| `PREVIEW_DATA (0x11)` | `preview` | head bytes |
| `CHAT (0x12)` | `chat` | chat JSON |
| `CLIPBOARD (0x13)` | `clipboard` | clipboard JSON |

Rules:

* Nonces are 12 random bytes per envelope (never reused under the same key).
* AAD binds ciphertext to its frame type — a sealed chunk cannot be replayed as a sealed chat message and vice versa.
* Control frames (ACKs, bitmaps, pause/resume) stay **plaintext** — they carry indices and booleans only.
* The signaling-relayed manifest can also be sealed for the server path as the string envelope `enc1.<hex(nonce||ct)>`.
* Downgrade behavior: if a peer does not complete the PAKE (e.g. the headless CLI, which is plaintext-only), the web sender proceeds after a **visible downgrade warning** and sends plaintext frames — the receiver-side guard freezes the "expect encryption" flag *after* a completed handshake only, so a never-started handshake cannot cause a stuck transfer. A handshake that *completed* and then a plaintext frame → rejected (injection guard).

### 7.3 Composition ordering (normative)

```
gzip-then-encrypt:  original ─► gzip ─► AES-GCM ─► CHUNK_ENC frame
decrypt-then-gunzip: CHUNK_ENC ─► AES-GCM⁻¹ ─► gunzip (iff manifest.compression) ─► store
```

## 8. Transfer manifest schema

Sent as the `MANIFEST` body (or plaintext of `MANIFEST_ENC`). JSON, UTF-8, `JSON.stringify` of:

```jsonc
{
  "transferId": "a1b2c3d4-e5f6-4a7b-8c9d-0e1f2a3b4c5d", // UUID v4 (crypto.randomUUID)
  "version": 1,                                           // exactly 1
  "files": [
    {
      "name": "report.pdf",                               // ≤ 255 chars, non-empty
      "size": 150000,                                      // bytes
      "type": "application/pdf",                           // MIME, non-empty
      "lastModified": 1716000000000,                      // epoch ms (source file mtime)
      "checksum": "<64-char lowercase hex SHA-256>",       // over the file's bytes
      "relativePath": "report.pdf"                         // webkitRelativePath or name
    }
  ],
  "totalSize": 200000,        // == sum(files[].size)
  "totalChunks": 4,           // == ceil(totalSize / chunkSize)
  "chunkSize": 65536,         // == 64 KiB in v1 (constant, see §8.2)
  "createdAt": 1717000000000, // epoch ms
  "expiresAt": 1717086400000, // createdAt + 24 h (resume record TTL)

  // OPTIONAL (v1.1): wire compression for chunk payloads
  "compression": "gzip",

  // OPTIONAL (v4 / 1.7): streaming Merkle tree over per-chunk SHA-256 leaves
  "merkle": {
    "root": "<64-char lowercase hex SHA-256 of root node>",
    "leaves": 4  // == totalChunks
  }
}
```

### 8.1 Invariants (checked by the conformance suite)

1. `version === 1`.
2. `totalChunks === ceil(totalSize / chunkSize)`.
3. `sum(files[].size) === totalSize`.
4. `expiresAt > createdAt`.
5. Every `files[].checksum` is 64-char lowercase hex; every `name` is 1–255 chars.
6. `files.length ≤ 100` (`MAX_FILES_PER_TRANSFER`); per-file and total size ≤ 10 GB (`MAX_FILE_SIZE`).
7. `transferId` matches UUID format.
8. `compression`, when present, is exactly the string `"gzip"`.
9. `merkle.leaves`, when present, equals `totalChunks`; `merkle.root` is 64-char lowercase hex.
10. JSON roundtrip preserves all fields (the wire body is byte-equal to `JSON.stringify(manifest)`).

Limits (reference constants, `protocol.ts`): `CHUNK_SIZE 65536` · `MAX_BUFFERED_BYTES 32 MiB` · `TARGET_BUFFERED_BYTES 8 MiB` · flow window `256 KiB … 16 MiB` (AIMD) · `GZIP_MIN_TRANSFER_BYTES 4096` · `MAX_FILE_SIZE 10 GiB` · `MAX_FILES_PER_TRANSFER 100` · `MAX_FILE_NAME_LENGTH 255` · blocked extensions `.exe .bat .cmd .com .scr .vbs .js .jar .msi .dll .sh`.

### 8.2 `chunkSize`

Fixed at 64 KiB per manifest in v1 — resume byte-offsets depend on it, so it never changes *within* a transfer. (The send path may opportunistically use the negotiated SCTP max-message-size for freshly-created transfers; the manifest value is authoritative for the receiver's reassembly math.)

### 8.3 Chunk addressing — the concatenated transfer stream

Files are sent as ONE contiguous byte stream, chunked at `chunkSize` boundaries:

```
global stream : [ file0 bytes ][ file1 bytes ]...[ fileN-1 bytes ]
chunk i       : stream[i*chunkSize, (i+1)*chunkSize)
```

A chunk may therefore **span file boundaries** (e.g. two small files sharing one 64 KiB chunk). Receivers slice each chunk back into files using the manifest's cumulative offsets (the reference implementation builds a "slice plan" and resolves each chunk index to per-file segments). `checksum` verification is per file.

### 8.4 Merkle field (v4 / 1.7)

When present, the sender computed one SHA-256 leaf per stored chunk during manifest hashing and sealed the root. The receiver rebuilds the identical tree from the bytes it actually stored and compares roots at completion; a mismatch localizes corruption to a subtree (binary descent over the leaves) so only affected chunks are wiped for re-request. Optional: older receivers ignore the field.

## 9. Signaling protocol (Socket.IO)

Server: standalone socket.io service on **:3003**, path `/socket.io`, CORS `*`, `maxHttpBufferSize` 1 MB (signaling only). Two plain HTTP endpoints: `GET /healthz` → `{ ok, rooms, uptimeSec }`, and `GET /turn-credentials` → `{ enabled: false }` or `{ enabled: true, ttlSeconds: 600, realm, iceServers: [{ urls, username, credential }] }` (coturn static-auth-secret HMAC-SHA1, short-lived). Clients use STUN-only when TURN is not configured.

### 9.1 Rooms, codes, PINs, TTLs

* **Room id:** 6 chars, alphabet `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (no ambiguous chars), server-generated, unique.
* **Join code:** 6 chars, same alphabet, returned to the creator (`room-created`) — a convenience for the join UI.
* **PIN:** 6 decimal digits (`crypto.getRandomValues`), only if the creator asked (`withPin`). Required by `join-room` when set. Wrong-PIN attempts are rate-limited per socket: **5 failures → 60 s lockout** (`signaling-error` code `RATE_LIMITED`).
* **Device cap:** default **8** devices/room (`MAX_DEVICES_PER_ROOM`, env-tunable, clamped 2–32) — 1 sender + N−1 receivers.
* **TTLs:** unpaired rooms expire after **5 min** (`ROOM_TTL_MS`); connected/transferring rooms are reaped after **30 min idle** (`ROOM_IDLE_TTL_MS`); receiver resume records live **24 h** client-side (`RESUME_RECORD_TTL_MS`). Expiry emits `room-expired { roomId, reason: 'timeout'|'idle' }` then `room-closed`.
* **QR:** `room-created` includes `qrData = fluxdrop://room/<roomId>?pin=<pin>`.

### 9.2 Event reference

All relay events are **unicast to the addressed device** (`to` field) with server-side membership verification; the server never looks inside `e2e-relay` payloads. Times are epoch ms. `RTCSessionDescriptionInit`/`RTCIceCandidateInit` are the standard WebRTC JSON shapes.

**Client → server**

| Event | Payload |
|---|---|
| `create-room` | `{ alias, deviceId, role: 'sender'\|'receiver', withPin?: bool }` |
| `join-room` | `{ roomId, joinCode?, pin?, alias, deviceId, role }` |
| `rejoin-room` | `{ roomId, deviceId, alias?, role?, pin? }` — socket.io gives a NEW socket.id on reconnect; this rebinds a known device (no PIN re-check if still registered, PIN re-added after disconnect-cleanup race) |
| `pairing-request` | `{ roomId, from, to, transferSummary?: { fileCount, totalSize, totalName } }` |
| `pairing-confirm` | `{ roomId, from, to, accepted }` |
| `pairing-reject` | `{ roomId, from, to, reason? }` |
| `webrtc-offer` | `{ roomId, from, to, sdp }` |
| `webrtc-answer` | `{ roomId, from, to, sdp }` |
| `webrtc-ice` | `{ roomId, from, to, candidate }` |
| `transfer-manifest` | `{ roomId, from, to, manifest }` — metadata relay for UI; may be an `enc1.<hex>` sealed string under E2E |
| `transfer-accepted` | `{ roomId, from, to, accepted, reason? }` |
| `transfer-complete` | `{ roomId, from, to }` |
| `transfer-cancel` | `{ roomId, from, to, reason? }` |
| `resume-request` | `{ roomId, from, to, transferId, lastChunkIndex }` |
| `resume-response` | `{ roomId, from, to, transferId, accepted, fromChunkIndex? }` |
| `e2e-relay` | `{ roomId, from, to, data }` — opaque PAKE blob (§7.1) |
| `heartbeat` | `{ roomId }` — touches `lastActivityAt` |
| `leave-room` | `{}` |

(`rejoin-room` is intentionally absent from the client `SIGNALING_EVENTS` constant — it is an internal signaling-client reconnect mechanism, but it is part of the server contract.)

**Server → client**

| Event | Payload |
|---|---|
| `room-created` | `{ roomId, joinCode, pin, qrData, device }` |
| `room-joined` | `{ roomId, joinCode, device, peers: Device[] }` — existing members, sender first |
| `room-expired` | `{ roomId, reason: 'timeout'\|'idle' }` |
| `room-closed` | `{ roomId }` |
| `device-discovered` | `{ device }` — a new member joined |
| `device-left` | `{ deviceId }` |
| `signaling-error` | `{ code, message }` — codes: `INVALID_INPUT`, `ROOM_NOT_FOUND`, `ROOM_FULL`, `RATE_LIMITED`, `INVALID_PIN`, `NOT_MEMBER`, `INTERNAL` |

`Device = { id, socketId, alias, role, joinedAt }` (server-side shape; clients see `id, alias, role`).

### 9.3 Connection sequence (happy path)

```
sender                                    receiver
  │ emit create-room {withPin:true}          │
  │◄─ room-created {roomId,joinCode,pin}     │
  │        (user shares room code + PIN)     │
  │                                          │ emit join-room {roomId, pin}
  │◄─ device-discovered {device} ───────────── room-joined {peers:[sender]}
  │                                          │ emit pairing-request {to: sender}
  │◄─ pairing-request                        │
  │ emit pairing-confirm {accepted:true} ────►│
  │ emit webrtc-offer {sdp} ─────────────────►│
  │◄─ webrtc-answer {sdp} ─────────────────── │
  │◄─ webrtc-ice ──────► (trickle, both ways)─►│
  │      [DataChannel 'fluxdrop-0' opens]     │
  │ (optional e2e-relay PAKE, §7.1)           │
  │ MANIFEST(_ENC) ──────────────────────────►│
  │◄─ PREVIEW_REQ ──► PREVIEW_DATA (≤4s) ─────│
  │◄─ MANIFEST_ACK {accepted:true}            │
  │ CHUNK_DATA × N ────────────────────────►  │
  │◄─ CHUNK_ACK × N                           │
  │ TRANSFER_COMPLETE {finalChecksum} ────────►│
  │◄─ TRANSFER_COMPLETE_ACK {verified:true}   │
```

### 9.4 Keep-alive

Signaling socket.io keeps the room's `lastActivityAt` fresh via `heartbeat` (reference cadence 30 s; also touched by every relayed event). `pingTimeout 60 s`, `pingInterval 25 s` on the server. DataChannel-level pauses (§5.10) rely on this to survive long pauses without the room being reaped.

## 11. Transfer lifecycle & sequencing rules

### 11.1 State machine (reference)

```
IDLE → VALIDATING → PAIRING → CONNECTING → MANIFEST_EXCHANGE → TRANSFERRING
     → VERIFYING → COMPLETE
                    ↘ PAUSED ↔ TRANSFERRING
                    ↘ CANCELLED | FAILED | ERROR
     any ─(connection lost)→ RETRYING/RESUMING → TRANSFERRING
```

### 11.2 Flow control & pacing (sender, per peer)

* **In-flight budget (AIMD):** start at 8 MiB; host↔host ICE pairs start at 16 MiB, relayed at 4 MiB; grow ×1.25 after 64 clean sends, halve on send-queue pressure; floor 256 KiB. Chunk *size* stays fixed per manifest — only the window adapts.
* **Buffer thresholds:** stop enqueueing at 32 MiB `bufferedAmount`; resume toward an 8 MiB target on `bufferedAmountLow` (threshold = max(window/4, 64 KiB)).
* **ACK pacing:** the receiver ACKs every chunk immediately; the sender uses ACKs as the growth signal and treats a re-delivered (lost-ACK) chunk as already-counted.
* **Parallel channels:** secondary DataChannels `fluxdrop-1..n` on the same SCTP association (shared congestion window — modest queuing gains only). Chunk *assignment* stays per-channel sequential from the shared plan.

### 11.3 Error handling

| Failure | Rule |
|---|---|
| Frame < 9 bytes | Malformed — decoder throws; error path, connection stays |
| Unknown opcode | Per-transfer protocol error (graceful fail), not connection teardown |
| Non-JSON control body | Fail-soft: `body = {}` |
| GCM auth failure (E2E) | Frame rejected; for manifest/chunk frames the transfer aborts (fail closed) |
| Preview/chat failure | Silently dropped — never disturbs the transfer |
| Checksum mismatch at completion | `TRANSFER_COMPLETE_ACK {verified:false}` → re-send path (Merkle-localized if `merkle` present) |

## 12. Extensibility rules

1. **New opcodes:** append-only (`0x14+`). Receiving an unknown opcode is a per-transfer error today; do not repurpose existing values.
2. **New manifest fields:** additive, optional, ignored by older peers (see `compression`, `merkle`). Anything that changes *receiver reassembly math* (e.g. a new `chunkSize`) must be a new manifest `version`.
3. **New JSON fields on control frames:** additive and optional — receivers read defensively (`body?.field`).
4. **New E2E AAD purposes:** new purpose strings may be added; the four-char set is fixed for existing frames (§7.2). AAD changes are a hard interop break — never remap.
5. **Signaling:** server events may be added; existing payloads only gain optional fields. The server stays data-blind: any future relay event must keep file bytes off it.
6. **Version bumps:** `manifest.version` gates receiver-side structural changes. Wire header layout is frozen — 9 bytes, no version field, ever (the opcode space is the versioning surface).
